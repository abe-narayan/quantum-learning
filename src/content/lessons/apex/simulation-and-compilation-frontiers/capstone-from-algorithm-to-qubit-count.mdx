export function smallestOddAtLeast(x) {
  let n = Math.ceil(x);
  if (n % 2 === 0) n += 1;
  return n;
}

## Motivation

Five lessons built one running capability: **Tensor Networks and Matrix
Product States** gave a classical simulation method and a number, bond
dimension, that measures how much entanglement it can afford; **When
Classical Simulation Works** turned that into a sharp boundary, exactly
which circuits a classical computer can already simulate efficiently, so
that "build a quantum computer" is a conclusion, not a default; **Clifford+T
Synthesis and Resource Counting** showed that once a circuit is past that
boundary, what it actually costs is measured in T-count, not gate count in
general; **Noise-Aware Compilation and Resource Estimation** showed that a
real device's limited connectivity inflates that gate count further, via
SWAP-heavy routing, before a single logical operation ever reaches
hardware; and **Quantum Simulation of Molecules** supplied the flagship
application, a Trotterized time-evolution circuit for a molecular
Hamiltonian, whose gate count every earlier stage in this list can be
applied to.

This capstone's only job is to chain those stages together, then hand the
result to the *other* capstone this pillar already built.

## Mathematical Development

### Stage 1 — is this classically simulable at all?

Before spending one more line of arithmetic on compiling this circuit,
When Classical Simulation Works demands the first, often-skipped
question: *can a classical computer already do this?* A state vector
for `toyQubitCount` = **{toyQubitCount}** qubits has
`hilbertSpaceDimension` = **{hilbertSpaceDimension}** complex amplitudes.
That is not merely "efficiently simulable" in the asymptotic sense that
lesson formalized — it is trivial, well within what a laptop simulates
in microseconds, for any circuit depth. **A real quantum computer would
be entirely the wrong tool for this exact toy circuit.** This is stated
plainly, not glossed over: the point of an example this small is
pedagogical, walking every downstream stage by hand, not a claim of
quantum advantage. Quantum Simulation of Molecules' own real published
estimates, for molecules with active spaces of dozens to hundreds of
qubits, are what actually cross this boundary; this toy circuit is
deliberately kept on the classically-trivial side of it so its numbers
stay checkable by hand through every remaining stage.

### Stage 2 — raw T-count via synthesis

Treat the rest of this pipeline as a hypothetical: *if* this circuit's
shape were scaled up to a regime past Stage 1's boundary, what would
Clifford+T Synthesis and Resource Counting say its T-count costs? T
gates are the resource that lesson identified as the one Clifford+T
synthesis cannot make free, so the running total that matters most is
built from them alone:

$$
N_T = (\text{T gates per step}) \times (\text{Trotter steps}) = 30 \times 20 = 600.
$$

That is `totalTGates` = **{totalTGates}**, a simple, explicit
multiplication with no synthesis subtlety hidden in it: the per-step
T-count was already stated as a given illustrative number, so Stage 2's
whole job is just accounting for how many steps repeat it. The
circuit's other gates are two-qubit Clifford gates, $50$ per step:

$$
N_2^{\text{raw}} = 50 \times 20 = 1000,
$$

`totalTwoQubitGates` = **{totalTwoQubitGates}**. Summing both gate
types gives the circuit's raw, pre-compilation gate count,
`rawTotalGateCount` = **{rawTotalGateCount}**.

### Stage 3 — routing overhead

Noise-Aware Compilation and Resource Estimation showed that a device's
limited connectivity, not an idealized fully-connected graph, forces a
compiler to insert extra SWAP gates before a logical two-qubit gate
between non-adjacent qubits can execute. Reusing that lesson's own
illustrative overhead magnitude, a `swapOverheadMultiplier` of
**{swapOverheadMultiplier}×** applied to the two-qubit gate count (T
gates are single-qubit non-Clifford rotations, unaffected by
two-qubit routing) gives the actual, post-compilation two-qubit gate
count a real device would need to execute:

$$
N_2^{\text{routed}} = N_2^{\text{raw}} \times 2.5 = 1000 \times 2.5 = 2500,
$$

`routedTwoQubitGates` = **{routedTwoQubitGates}**. Adding back the
(routing-unaffected) T-count gives the routed total gate count that
Stage 4 actually needs as input:

$$
N_{\text{routed}} = N_T + N_2^{\text{routed}} = 600 + 2500 = 3100,
$$

`routedTotalGateCount` = **{routedTotalGateCount}**. Routing alone
nearly doubled the circuit's total gate count, from
{rawTotalGateCount} to {routedTotalGateCount}, purely from the device's
connectivity constraint, before a single fault-tolerance
consideration has entered the calculation.

### Stage 4 — the Fault Tolerance Frontiers capstone's own methodology, reused exactly

This is the handoff. Capstone: Resource Estimation for a Real
Algorithm derived a four-step pipeline from "$N_T$ T gates, $N_2$
two-qubit gates, target overall success probability" to "total physical
qubits," and nothing about that derivation was specific to its own toy
$N_T=100$, $N_2=500$ pair. Plugging in *this* lesson's Stage 2/3 outputs
instead — $N_T = 600$, $N_2 = N_2^{\text{routed}} = 2500$, so
$N_T+N_2 = 3100$ — and the same $99\%$ overall-success target used
there:

**Step (a), per-gate error budget (union bound):**

$$
p_L^{\text{target}} = \frac{0.01}{3100} \approx 3.226\times10^{-6},
$$

`perGateBudget` = **{perGateBudget.toExponential(3)}** — noticeably
tighter than the fault-tolerance capstone's own $1.667\times10^{-5}$,
simply because this pipeline's routing overhead left more gates that
all have to succeed.

**Step (b), code distance from the threshold scaling law.** At the
same operating point that capstone used, $p = p_{\mathrm{th}}/10$ so
$p/p_{\mathrm{th}} = 0.1$:

$$
d \ge 2\,\frac{\ln p_L^{\text{target}}}{\ln(p/p_{\mathrm{th}})} - 1,
$$

`minCodeDistanceRaw` = **{minCodeDistanceRaw.toFixed(3)}**, so the
smallest odd admissible distance is `codeDistance` =
**{codeDistance}** (one step up from that capstone's $d=9$ — the
tighter budget here costs two extra rows and columns of the lattice).
Checking: `achievedLogicalErrorRate` =
**{achievedLogicalErrorRate.toExponential(3)}**, comfortably under the
{perGateBudget.toExponential(3)} target.

**Step (c), magic-state factory sizing.** Magic States and
Distillation's $35\,p_{\text{in}}^3$ formula, applied at
$p_{\text{in}} = p = 0.001$ exactly as before:

$$
p_{\text{out}} = 35\,(0.001)^3 = 3.5\times10^{-8},
$$

`distillationOutputError` = **{distillationOutputError.toExponential(2)}**,
still `magicStateHeadroom` = **{magicStateHeadroom.toFixed(0)}×** below
the tighter {perGateBudget.toExponential(3)} target — smaller headroom
than the fault-tolerance capstone's $476\times$, exactly because this
pipeline's budget is tighter, but still enough that one level of
$15$-to-$1$ distillation suffices; no second level is needed for this
toy circuit's $600$ T gates.

**Step (d), total physical qubit count.** A distance-$d$ patch costs
`dataQubitsPerPatch` = **{dataQubitsPerPatch}** data qubits and
`ancillaQubitsPerPatch` = **{ancillaQubitsPerPatch}** ancilla qubits,
`qubitsPerLogicalPatch` = **{qubitsPerLogicalPatch}** total. This toy
molecular circuit needs `logicalQubitCount` = **{logicalQubitCount}**
logical qubits (Stage 1's own $2$-qubit toy Hamiltonian):

$$
\text{data} = 2\times121 = 242,\qquad \text{ancilla} = 2\times120=240,
$$

`totalDataQubits` = **{totalDataQubits}**, `totalAncillaQubits` =
**{totalAncillaQubits}**, `computeQubits` = **{computeQubits}**. The
factory needs $15$ patches at the same distance:

$$
\text{factory} = 15\times241 = 3615,
$$

`factoryQubits` = **{factoryQubits}**. Summing all three:

$$
N_{\text{physical}} = 242+240+3615 = 4097,
$$

`totalPhysicalQubits` = **{totalPhysicalQubits}** — the single number
this entire five-lesson-plus-capstone pipeline was built to produce.
The factory alone is `factoryShareOfTotal` =
**{(factoryShareOfTotal * 100).toFixed(1)}%** of the total, an even
larger share than the fault-tolerance capstone's own $71.4\%$, because
this toy circuit's logical-qubit count ($2$) is smaller relative to the
fixed $15$-patch factory than that capstone's ($6$) was — the same
$15/(15+L)$ relationship derived there, just evaluated at a smaller
$L$.

## Physical Interpretation: what's solid, and what's still research

<Callout type="note">
**Not every stage of this pipeline carries the same epistemic weight,
and pretending otherwise would misrepresent the field.** Stages 1
through 3, checking classical simulability, counting T-count via
Clifford+T synthesis, and estimating routing overhead from a device's
connectivity graph, are well-established, routine engineering practice
today. Real compiler toolchains (Qiskit's transpiler, tket, and others)
run exactly these steps automatically for near-term circuits, on real
hardware coupling graphs, every day. There is no open research question
about *how* to compute a T-count from a decomposed circuit or *how* to
estimate SWAP overhead from a device's connectivity; those are solved,
implemented, engineering problems.
</Callout>

Stage 4 is a different kind of claim. The four-step
error-budget/code-distance/distillation/qubit-count methodology itself
is solid, real published estimates use exactly this structure. But the
*numbers that methodology outputs* depend on assumptions that are still
moving targets as the field's engineering matures: the achieved
physical error rate $p$ a real device reaches (this lesson assumed
$p_{\mathrm{th}}/10$ throughout, matching the fault-tolerance capstone,
but real hardware roadmaps disagree on when and whether that specific
ratio is achieved at scale), the real-time decoder's throughput and
accuracy (a decoder too slow to keep up with syndrome extraction stalls
the whole computation, regardless of what the code distance formula
says on paper), and the specific code and architecture choice (surface
codes are what this pillar derived, but qLDPC and other code families
under active research promise substantially lower physical-to-logical
qubit ratios, which would shrink every qubit count in Stage 4 without
changing Stages 1 through 3 at all). A reader who takes away "physical
qubit counts for fault-tolerant algorithms are precisely known" has
misread this lesson; a reader who takes away "the *method* for
estimating them is solid, and the inputs to that method are where the
real uncertainty and the real research lives" has read it correctly.

This full pipeline, Stages 1 through 4 together, is the APEX pillar's
practical answer to a question popular accounts of quantum computing
routinely skip: *given a quantum algorithm I've just read about, how
would I actually estimate whether it's realistically achievable, and on
what timescale?* Check classical simulability first. Count real
T-gates. Account for real device connectivity. Then, and only then,
apply fault-tolerance overhead, honestly labeling which of those four
answers is engineering fact and which is a current best guess.

## Common Mistakes

<Callout type="mistake">
**Skipping Stage 1 and jumping straight to compiling.** It is tempting
to treat "count the gates, then estimate qubits" as the whole pipeline.
But a circuit that is already classically simulable, like this
lesson's own $2$-qubit toy example, gains nothing from the remaining
three stages except pedagogical value. When Classical Simulation
Works exists precisely so this check happens *first*, before any
compilation effort is spent on a circuit that never needed a quantum
computer at all.
</Callout>

<Callout type="mistake">
**Applying the routing multiplier to the T-count.** Stage 3's
{swapOverheadMultiplier}× overhead comes from inserting SWAP gates to
route two-qubit interactions across limited connectivity; it has
nothing to do with T gates, which act on a single qubit and never need
routing to a neighbor. Multiplying `totalTGates` by
{swapOverheadMultiplier} instead of leaving it untouched would inflate
$N_T$, and therefore the magic-state factory sizing in Stage 4c, for no
physical reason.
</Callout>

<Callout type="mistake">
**Treating the {totalPhysicalQubits}-qubit answer as equally certain
across all four stages.** As the Physical Interpretation section
argued, Stages 1–3 are routine engineering with essentially no
methodological uncertainty; Stage 4's *method* is solid but its
specific numeric inputs ($p$, decoder performance, code choice) are
still evolving. Quoting {totalPhysicalQubits} as a hard, precise
prediction misrepresents how much of that number rests on assumptions
still under active research.
</Callout>

## Summary

- The full pipeline this capstone connects has four stages: (1) check
  classical simulability first (When Classical Simulation Works) —
  this lesson's own $2$-qubit toy circuit fails this check trivially,
  by design; (2) count T-gates via Clifford+T synthesis, a simple
  multiplication here giving $N_T=600$; (3) apply a device's
  routing/SWAP overhead (Noise-Aware Compilation), inflating the
  two-qubit gate count from {totalTwoQubitGates} to
  {routedTwoQubitGates} and the total to {routedTotalGateCount}; (4)
  hand $N_T$ and the routed $N_2$ to the Fault Tolerance Frontiers
  capstone's own four-step methodology unchanged, producing a code
  distance of {codeDistance} and a final estimate of
  {totalPhysicalQubits} total physical qubits.
- That last number is over a thousand times the circuit's own
  {logicalQubitCount} logical qubits, and the magic-state factory alone
  is {(factoryShareOfTotal * 100).toFixed(1)}% of it — the same
  factory-dominance finding the fault-tolerance capstone reached,
  recurring here at a different logical-qubit count.
- Stages 1–3 are solved, routine engineering practice; Stage 4's
  *method* is equally solid, but its numeric inputs (achieved physical
  error rate, decoder throughput, code/architecture choice) are still
  active research, and an honest resource estimate says so explicitly
  rather than presenting every stage as equally certain.
