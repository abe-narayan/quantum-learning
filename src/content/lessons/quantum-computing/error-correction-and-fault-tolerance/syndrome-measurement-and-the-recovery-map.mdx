## Motivation

Every code this course has built follows the same four-step procedure. This
lesson names that procedure in general terms and then gives the standard
notation, $[[n,k,d]]$, that lets two codes be compared at a glance.

The notation is worth the effort because it makes one thing impossible to
hide. A code's distance has to be quoted against a specific error model,
and the 3-qubit bit-flip code, which sounds like a distance-3 code, is
distance 1 as a general quantum code. The parameters say so out loud.

## Mathematical Development

### The recovery procedure, in general

For any stabilizer code with generators $g_1,\dots,g_m$:

1. **Measure every generator** $g_i$, obtaining a syndrome bit for each
   (via ancilla-based measurement, as Lesson 2 built, never
   measuring the data qubits directly).
2. **Look up the syndrome** in a precomputed table mapping syndrome
   patterns to the most likely error.
3. **Apply the matching correction** (a Pauli operator, or product of
   Paulis, that reverses the identified error).
4. The corrected state is guaranteed to be back in the code space,
   *exactly* the original encoded state, for any error the code was
   designed to handle.

This is `runBitFlipCorrectionCycle`'s four steps (extract
syndrome via ancilla CNOTs and measurement, `decodeBitFlipSyndrome` looks
up the table, apply $X$ to the identified qubit, return the corrected
3-qubit state), described here in the vocabulary that generalizes to any
stabilizer code, not just this one.

### Code parameters: [[n,k,d]]

A quantum code is described by three numbers: $n$ (physical qubits used),
$k$ (logical qubits protected), and $d$ (the code's **<Term id="code-distance">distance</Term>**, the
minimum number of physical qubits an *undetectable* error must act on).
Against bit-flip errors alone, the 3-qubit code earns distance $3$: $3$
physical qubits, $1$ logical qubit, and the cheapest undetectable $X$-type
error has weight 3 ($X$ on all three qubits maps
$|000\rangle\leftrightarrow|111\rangle$ while leaving both
$Z_0Z_1$ and $Z_1Z_2$ syndromes at $(0,0)$; no weight-1 or weight-2 $X$
error does this). As a general quantum code, though, its distance is only
$1$. A single $Z$ on any one qubit commutes with both stabilizers, so the
syndrome stays $(0,0)$, yet it sends
$\alpha|000\rangle+\beta|111\rangle$ to
$\alpha|000\rangle-\beta|111\rangle$: an undetectable weight-1 error that
changes the logical state. This is the $Z$-blindness the course flagged
when the code was first built, restated in code-parameter language, and it
is why the Shor code exists. The Shor code is a true $[[9,1,3]]$, distance
$3$ against *every* Pauli error type, at $3\times$ the physical qubit
cost.

Distance $3$ against one error type versus distance $3$ against all of
them, at $3\times$ the qubits: $n$ is a cost paid for broader error
coverage, not a benefit that scales with the number itself.

### Distance and correctable error count

A distance-$d$ code corrects any error affecting **fewer than $d/2$**
physical qubits, the same relationship classical coding theory uses. The
distance must be quoted for the error model in question: the bit-flip
code's $d=3$ holds only against $X$ errors, so "corrects any single-qubit
error ($1<3/2$)" means any single-qubit *bit-flip* error, which is what
Lessons 2 and 3 verified directly. A two-qubit error is not guaranteed
correctable by a distance-3 code (consistent with the practice question,
several lessons back, about simultaneous errors on two data qubits).

## Physical Interpretation

$[[n,k,d]]$ makes the fundamental tradeoff of quantum error correction
explicit: larger $d$ (more error-correcting power) generally costs more
physical qubits $n$ per logical qubit $k$, the resource-overhead
question the capstone returns to with concrete numbers for real
fault-tolerant architectures.

Real devices add a constraint this lesson's lookup-table decode doesn't
face at 3-qubit scale: speed. A physical qubit keeps <Term id="noise-decoherence">decohering</Term> while
the syndrome is being measured and decoded, so the correction has to be
computed and applied before that error information goes stale. Google's
2023 <Term id="surface-codes">surface-code</Term> experiments paired syndrome extraction with a
classical decoder running fast enough to keep pace with the device's
measurement rate: a real-time computing problem sitting on top of the
decode-table lookup this lesson builds, and one that gets harder as $n$
grows and the lookup table stops being a table at all.

## Worked Example

**Confirm the bit-flip code's distance against $X$ errors is exactly 3,
not less, by checking what happens for a weight-1 and a weight-2 $X$
error.**

A weight-1 error (single $X$) always flips at least one of $Z_0Z_1,Z_1Z_2$
(shown directly in Lesson 5), always detected and correctly reversed, as
Lesson 2 verified. A weight-2 error, $X_0X_1$: syndrome from $Z_0Z_1$ is
unchanged (both qubits it touches flipped together, preserving their
parity), but $Z_1Z_2$'s syndrome *does* flip (qubit 1 flipped, qubit 2
didn't), giving syndrome $(0,1)$, which the decode table reads as "error
on qubit 2." Applying the recovery procedure's prescribed fix, $X_2$, to
the already-corrupted state gives a net applied error of
$X_0X_1\cdot X_2=X_0X_1X_2$, the weight-3 logical error
identified below, so "recovery" here doesn't fail gently: it actively
converts a 2-qubit error into a full logical bit flip
($\alpha\leftrightarrow\beta$), confirmed directly by the engine (a
$0.6,0.8$ encoding, hit by $X_0X_1$ and "recovered," comes out as
$0.8,0.6$, swapped). Only the weight-3 error $X_0X_1X_2$ on its own,
with no recovery attempted, is truly undetectable at the syndrome stage
($Z_0Z_1$: both flip, parity preserved; $Z_1Z_2$: both flip, parity
preserved) while still swapping $\alpha\leftrightarrow\beta$: an error
that leaves no trace in the syndrome at all, confirming $d=3$ within
the bit-flip error model. (For the full-Pauli distance, remember the
single-$Z$ error from the parameters section: undetected, weight 1.)

## Common Mistakes

<Callout type="warning">
**Confusing "detected" with "safely handled."** The worked example's
weight-2 case *does* trigger a nonzero syndrome, but running the
recovery procedure on it doesn't just fail to help, it actively converts
the 2-qubit error into a full logical bit flip. A distance-3 code is only
guaranteed correct for weight-1 errors; running its recovery procedure on
a weight-2 error can make things categorically worse, not merely
"not better."
</Callout>

<Callout type="warning">
**Assuming bigger n always means a better code.** $n$ is a *cost*
(physical qubits spent), not a benefit. The meaningful comparison is the
ratio of $d$ (or correctable error count) to $n$, which is what makes
$[[9,1,3]]$ (Shor) less resource-efficient than later codes with the same
distance but fewer physical qubits (not covered in this course, but named
here as a real, active research area).
</Callout>

## Summary

- The general recovery procedure: measure every stabilizer, look up the
  syndrome, apply the matching correction, which is what Lesson 2's
  circuit already implements.
- $[[n,k,d]]$ notation: $n$ physical qubits, $k$ logical qubits, distance
  $d$. The bit-flip and phase-flip codes each reach distance 3 against
  their target error type, but only distance 1 against the full Pauli
  model; Shor's code is a true $[[9,1,3]]$.
- A distance-$d$ code corrects any error affecting fewer than $d/2$
  qubits within its error model, verified directly for the bit-flip
  code's weight-1 (corrected), weight-2 (detected but miscorrected), and
  weight-3 (undetectable) $X$-error cases.
