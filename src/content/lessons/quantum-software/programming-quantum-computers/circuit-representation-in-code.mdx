## Why Build a Description Instead of Running It

A quantum program is typically
built as a *description* of a circuit first (a list of instructions),
which is only later sent off to be executed (on a simulator or real
hardware). Why bother with the description, instead of just applying
each gate as the line of code runs?

The payoff for keeping the circuit as data shows up the moment the
target changes. A circuit written as immediate matrix applications is
welded to whatever machine ran it; a circuit written as an instruction
list is not, and can be re-aimed at a different backend without a line
of it being rewritten.

## Build First, Run Later

### The shape every SDK shares

Every major quantum SDK (Qiskit, Cirq, PennyLane, and others) follows
the same basic shape: construct a circuit object by appending gate
instructions to it, then pass the finished circuit to a separate
execution step. This isn't just stylistic. It's what allows a circuit
to be inspected, optimized (Compilation & Hybrid Algorithms' own
<Term id="quantum-compilation-transpilation">transpilation</Term> lesson), or sent to different backends (a simulator today,
real hardware tomorrow) without rewriting the circuit itself.

### This platform's QuantumCircuit

```
const circuit = new QuantumCircuit(2);
circuit.h(0).cnot(0, 1);
const state = runCircuit(circuit);
```

`circuit.h(0).cnot(0,1)` doesn't touch any <Term id="quantum-state">quantum state</Term> at all. It
appends two `GateInstruction` objects (plain data: `{gate:"H",
targets:[0]}` and `{gate:"CNOT",targets:[0,1]}`) to a list.
`runCircuit(circuit)` is the separate execution step: it starts from
$|00\rangle$ and dispatches each instruction to the same
`applySingleQubitGate`/`applyCNOT` functions Quantum Gates & Circuits
already used directly. No new gate physics, only a new way of
organizing *when* that physics runs.

### Why this separation matters

Because the circuit is just data until `runCircuit` is called, the same
circuit object can be executed multiple times (Qubit Readout Techniques'
multi-shot statistics), inspected instruction-by-instruction before
running (useful for debugging), or, in a real SDK, transformed by an
optimizer before ever touching real hardware. None of this is possible
if gates are applied immediately and irreversibly as each line of code
runs.

## Structure, Not Physics

No new physics enters here. `SINGLE_QUBIT_MATRICES` inside
`circuitBuilder.ts` holds the same `PAULI_X`, `HADAMARD`, and the rest,
imported from `gates.ts`. The content here is about *software structure*
rather than physics, which is a fair description of most quantum
programming work day to day: less deriving new matrices, more organizing
gate sequences correctly.

The three-instruction list this section's worked example builds,
`circuit.h(0).z(0).h(0)`, happens to read the same forwards and
backwards, which is exactly why it is safe to eyeball. Most circuits are
not palindromes, and the instruction list is what keeps the order
unambiguous.

## Expecting a State Before You Run

<Callout type="warning">
**Assuming `circuit.h(0)` immediately changes some quantum state.** It
only appends an instruction to a list. No quantum state exists at all
until `runCircuit` is called.
</Callout>

<Callout type="note">
**Thinking this is a different kind of quantum computing.** It is the
same physics: every instruction dispatches to Quantum Gates & Circuits'
own functions. Only the software organization has changed:
data-then-execute in place of immediate-execute.
</Callout>

## Practice Questions

1. After calling `circuit.h(0).cnot(0,1)` but BEFORE calling
   `runCircuit`, what (if anything) has happened to any quantum state?
   Then name two things that fact makes possible.

   <details className="answer-reveal">
   <summary>Answer</summary>

   **Nothing, because there is no quantum state yet.** Not an unchanged
   one; none at all.

   What the two calls did was append two plain objects to a list. Read
   the circuit's `instructions` array afterwards and it holds exactly

   `[{"gate":"H","targets":[0]},{"gate":"CNOT","targets":[0,1]}]`

   and nothing else. Each method also returns `this`, which is the only
   reason the calls chain. The starting $|00\rangle$ is created inside
   `runCircuit`, when execution begins, and it does not exist before
   that.

   The wrong turn is a reading habit rather than a misunderstanding of
   physics. Chained method calls that look like commands read as though
   they are doing something to an object's state, and in most code they
   would be. Here the object being mutated is the *instruction list*,
   which is a description of a program, and a description of an H gate is
   no more a quantum state than a recipe is a meal.

   The signature settles it. `runCircuit(circuit)` takes the circuit as
   an argument and *returns* a `StateVector`. If the circuit were already
   carrying a state, there would be nothing for that function to return
   and no reason for it to accept the circuit as input.

   Two consequences follow directly, and they are the payoff of the whole
   arrangement.

   The circuit is not consumed. Call `runCircuit` on the same object
   twice and you get two independent state vectors, which is precisely
   how multi-shot statistics are collected without rebuilding anything.

   And the circuit can be read. Print the list, inspect it
   instruction by instruction, or hand it to an optimizer, all before a
   single amplitude has been touched. Question 2 is about why that
   matters.

   </details>

2. Why does separating circuit construction from execution make later
   optimization (Compilation & Hybrid Algorithms) possible in a way that
   immediate execution would not?

   <details className="answer-reveal">
   <summary>Answer</summary>

   Because an optimizer transforms *programs*, and immediate execution
   destroys the program while producing its result.

   Think about what applying a gate immediately does. It multiplies a
   matrix into a state vector. The state vector afterwards holds the
   combined effect of everything applied so far, and it holds nothing at
   all about what those things were. Given a vector of amplitudes there
   is no way to recover the fact that it was reached by an H followed by
   a CNOT rather than by some other sequence with the same effect. The
   structure is gone, irreversibly, as soon as the multiplication
   happens.

   Every compiler transformation the later course applies needs exactly
   that structure back:

   **Algebraic simplification** needs to see neighbouring instructions.
   Two adjacent X gates cancel; $HZH$ collapses to $X$; a rotation
   followed by its inverse is nothing. Each of those is a statement about
   a pattern in the list, and none of them is visible in the resulting
   vector.

   **Routing** needs the whole circuit at once. Deciding where to insert
   SWAP gates so that every two-qubit instruction lands on a physically
   connected pair is a question about which pairs interact and in what
   order, over the entire program.

   **Scheduling** needs a dependency graph. Two gates on disjoint qubits
   can run in the same time slot, which shortens the circuit's depth and
   therefore its exposure to decoherence, and working out which gates
   those are means reading ahead.

   **Retargeting** needs the abstract instructions to survive. The same
   list can be lowered onto one machine's native gate set today and a
   different one tomorrow. Immediate execution has already committed to
   one interpretation.

   The single sentence version: immediate execution is a destructive
   fold, collapsing the program into its effect, while the instruction
   list keeps the program itself, and a compiler is a function from
   programs to programs.

   Two wrong turns.

   The first is "you could optimize by reading ahead in the source code
   instead." That is not an alternative to this design, it *is* this
   design. Reading ahead requires some representation of what is coming,
   and an instruction list is what that representation looks like once
   you build it deliberately rather than accidentally.

   The second is that the extra layer must cost performance, since
   building a list is work that immediate execution skips. It runs the
   other way for anything nontrivial. Applying two X gates that cancel
   means two full passes over $2^n$ amplitudes; noticing they cancel
   means comparing two small objects, and then doing neither pass. The
   list costs a few bytes per gate and saves exponentially sized work.

   </details>

3. Write out (in your own words, not code) the sequence of
   `GateInstruction` objects that `circuit.x(0).h(1).cnot(0,1)` would
   produce.

   <details className="answer-reveal">
   <summary>Answer</summary>

   Three objects, in call order:

   an X instruction targeting qubit 0, recorded as gate name `"X"` with a
   targets list holding the single entry 0;

   an H instruction targeting qubit 1, gate name `"H"`, targets list
   holding 1;

   a CNOT instruction, gate name `"CNOT"`, whose targets list holds two
   entries in a fixed order: the control, 0, first, then the target, 1.

   Verbatim from the engine, `circuit.instructions` is

   `[{"gate":"X","targets":[0]},{"gate":"H","targets":[1]},{"gate":"CNOT","targets":[0,1]}]`.

   Three details in that structure are worth noticing.

   **Order matters and is preserved.** The list is the program, and
   `runCircuit` walks it front to back. Nothing sorts or reorders it.

   **A two-qubit gate is not two instructions.** It is one instruction
   with two targets, which is what lets a router later ask "are these two
   qubits adjacent on the hardware?" as a single question about a single
   object.

   **`targets` is positional, not a set.** `[0,1]` means control 0,
   target 1. Swapping them to `[1,0]` is a genuinely different gate, so
   the ordering carries meaning that a set would lose.

   Now the part worth more than the transcription. Run this circuit and
   the probabilities come back as $[0,\ 0,\ 0.5,\ 0.5]$: the outcomes
   $|10\rangle$ and $|11\rangle$, equally likely. **That is a product
   state, not an entangled one, despite the circuit containing a CNOT.**

   Follow it through. X on qubit 0 takes $|00\rangle$ to $|10\rangle$. H
   on qubit 1 gives $(|10\rangle+|11\rangle)/\sqrt2$. The CNOT's control,
   qubit 0, is now in a *definite* $|1\rangle$, so the gate acts as a
   plain X on qubit 1 and simply swaps the two terms, leaving the same
   state it started from. The result is $|1\rangle\otimes|+\rangle$,
   perfectly separable.

   A CNOT only entangles when its control is itself in superposition,
   which is why the Bell circuit puts the H on the *control* and this one
   puts it on the target. Being able to see that from the instruction
   list, before running anything, is exactly the kind of reasoning
   keeping the circuit as data is for.

   </details>

4. Explain why `runCircuit`'s implementation needs no new gate-physics
   code beyond what Quantum Gates & Circuits' `gates.ts` already
   provides.

   <details className="answer-reveal">
   <summary>Answer</summary>

   Because `runCircuit` is a dispatcher, not a simulator. It contains no
   physics to be new.

   Its whole job is: create a $|0\dots0\rangle$ state, walk the
   instruction list, and for each entry decide which already-existing
   function to call. A single-qubit instruction looks its matrix up in
   `SINGLE_QUBIT_MATRICES`, a table whose entries are literally
   `PAULI_X`, `PAULI_Y`, `PAULI_Z`, `HADAMARD`, `S_GATE` and `T_GATE`
   imported from `gates.ts`, and hands it to `applySingleQubitGate`. A
   parametrized instruction calls `rotationX`, `rotationY`, `rotationZ`
   or `phaseGate` to build its matrix and then the same applier. A
   two-qubit instruction calls `applyCNOT`, `applyCZ` or `applySwap`.
   Every one of those was written and tested before this lesson existed.

   The reason this is possible at all is that the circuit-as-data layer
   changes *when* gate application happens and *how it is described*, not
   *what it is*. Those are orthogonal concerns, and the separation is the
   lesson's actual content: physics in `gates.ts`, software structure in
   `circuitBuilder.ts`.

   The evidence is in the numbers. Building $H$, $Z$, $H$ as an
   instruction list and running it returns probabilities
   $[0,\ 1.0000000000000004]$, which is the identity $HZH=X$ reproduced
   to floating-point precision, and is bit-for-bit what applying the same
   three matrices by hand gives. If the new layer had reimplemented
   anything, there would be some possibility of it disagreeing. There
   isn't, because there is nothing to disagree with.

   Two practical consequences.

   A bug fixed in `gates.ts` is fixed for every circuit ever built,
   because there is only one implementation of each gate in the codebase.

   And a bug in the circuit layer cannot silently produce wrong physics.
   It can dispatch to the wrong gate, target the wrong qubit, or lose an
   instruction, and all of those are loud, structural failures. It cannot
   quietly return an almost-right amplitude, because it never computes an
   amplitude.

   One instruction is the exception, and it is instructive. `MEASURE`
   does not touch the state vector at all: it is a diagram and notation
   marker recording "read this wire here." It is the one entry in the
   instruction vocabulary with no gate physics behind it, precisely
   because it is not a gate.

   The wrong turn is expecting a new abstraction layer to bring its own
   approximations, so that a "circuit simulator" is a distinct and
   presumably less exact thing than applying matrices directly. Here it
   is the same code path with a list in front of it.

   </details>

## Summary

- Real quantum SDKs build a circuit as data (a list of gate
  instructions) before executing it, a "build first, run later"
  pattern.
- This platform's `QuantumCircuit`/`runCircuit` implement this
  pattern, dispatching every instruction to the same gate functions
  Quantum Gates & Circuits already built and tested.
- This is a software-structure lesson, not new physics: the same
  content as this platform's matrix-heavy courses, organized
  differently.
